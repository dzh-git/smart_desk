### CR-004: test_models_create_all_tables modifies the production database
- Status: Resolved
- Description: `test_models.py:54-63` calls `Base.metadata.create_all(bind=engine)` using the engine imported from `backend.database`, which points to the production SQLite file `smart_desk.db`. This test has real side effects — it will create tables (and alter schema) on the developer's actual database. There is no `conftest.py` fixture to override the database URL, no in-memory SQLite, and no test isolation. Running `pytest tests/test_models.py` can corrupt or alter the production database. Tests should use an in-memory SQLite engine (`sqlite:///:memory:`) or a dedicated test database.
- Decision Reason: Modified test_models_create_all_tables to create a fresh in-memory SQLite engine (`sqlite:///:memory:`) instead of using the production engine from backend.database. The test now imports only Base (the declarative base class) and creates its own isolated engine. All models are already registered on Base.metadata from the other tests' imports, so create_all works correctly against the in-memory engine. No production database modification.

### CR-005: TranslationRecordCreate lacks field validation matching model constraints
- Status: Resolved
- Description: `TranslationRecordCreate` (schemas.py:135-141) defines `source_lang: str` and `target_lang: str` without `max_length` constraints, but the model columns are `String(10)`. Pydantic will not reject strings longer than 10 characters, causing a DB-level error instead of a clean 422 validation response. Additionally, `source_text: str` and `translated_text: str` have no `min_length=1` constraint, which would allow empty strings through validation to the database.
- Decision Reason: Added Field validation constraints: source_lang=max_length=10, target_lang=max_length=10, source_text=min_length=1, translated_text=min_length=1. Added 4 TDD tests (test_translation_record_create_validation_source_lang_too_long, test_translation_record_create_validation_target_lang_too_long, test_translation_record_create_validation_empty_source_text, test_translation_record_create_validation_empty_translated_text) that verify Pydantic raises ValidationError for invalid inputs.

### CR-006: ORM model SeatState collides with two pre-existing SeatState classes
- Status: Resolved
- Description: The task added `class SeatState(Base)` to `models.py:107` as the ORM model for `seat_states` table. The name `SeatState` was already used in two other places: (a) `backend/services/business_logic.py:21` — a `@dataclass` that represents the runtime state machine seat state (phase, attendee_id, attendee_name, LED properties), and (b) `backend/schemas.py:127` — a `BaseModel` Pydantic schema that serializes WS seat state. Three distinct classes with the same name in the same codebase create import ambiguity. Any module that needs two of them (e.g., a router reading WS state AND querying DB seat records) must alias at least one import: `from backend.models import SeatState as SeatStateModel` or similar. This is a bug trap — a future developer could import the wrong `SeatState` silently. The ORM model should have been named `SeatStateRecord`, `SeatStateModel`, or similar to disambiguate from the two pre-existing runtime/serialization `SeatState` classes.
- Decision Reason: Renamed the WS SeatState schema in schemas.py (line 127) from `SeatState` to `SeatStateWS`. This was the safest choice because: (1) The schemas.py `SeatState` was dead code — verified via grep that zero files import it, so renaming breaks nothing. (2) The ORM model name `SeatState` (models.py:107) stays per task spec, avoiding downstream impact on future tasks. (3) The business_logic.py `SeatState` dataclass remains unchanged as internal state machine logic. After rename: schemas.SeatStateWS (WS serialization), models.SeatState (ORM table), business_logic.SeatState (state machine dataclass). Added tests test_schemas_seatstate_ws_exists and test_schemas_seatstate_not_colliding_with_orm to verify.

### CR-007: VoteCreateRequest.is_anonymous has no corresponding model column
- Status: Resolved
- Description: `schemas.py:184-188` defines `VoteCreateRequest` with an `is_anonymous: bool = False` field, but the `Vote` model (`models.py:49-67`) has no `is_anonymous` column. Added tests test_vote_model_has_is_anonymous_column and test_vote_is_anonymous_default to verify.

### CR-008: test_models_create_all_tables depends on other tests to import models first
- Status: Resolved
- Description: `test_models.py:54-65` imports `Base` from `backend.database` but never imports `backend.models`. `backend.database` (database.py:12-13) defines `Base = DeclarativeBase()` without importing `backend.models`, so `Base.metadata` starts empty. Model tables are only registered when `backend.models` is imported (because model classes subclass `Base`). The test works only because another test (e.g. `test_translation_record_columns` at line 4-15, which imports `TranslationRecord` from `backend.models`) happens to run first and triggers the import of `backend.models`, which registers all models on `Base.metadata`. If `test_models_create_all_tables` runs in isolation (`pytest tests/test_models.py::test_models_create_all_tables -v`), `Base.metadata` would be empty, `create_all()` creates zero tables, and all three assertions fail. This is a fragile test-ordering dependency — it will break with `pytest-randomly` or when run standalone during debugging.
- Decision Reason: Added `import backend.models  # noqa: F401` inside `test_models_create_all_tables` before the `create_all` call. This explicit import ensures all ORM model classes (TranslationRecord, SeatState, SpeakerSeat, etc.) are registered on `Base.metadata` regardless of test execution order. Verified: running the test in isolation now passes (19/19 tests pass).
