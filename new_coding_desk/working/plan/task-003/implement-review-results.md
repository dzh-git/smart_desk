## Code Review Issues

### CR-001: datetime.utcnow() deprecated — forward-compatibility liability
- Status: Resolved
- Description: `meeting_repository.py:32` and `meeting_repository.py:34` use `datetime.utcnow()` to set `started_at` and `ended_at` timestamps in `update_status()`. This function returns a naive datetime (no timezone) and is deprecated in Python 3.12+ (PEP 615). The project targets Python 3.11+, so upgrading Python will trigger `DeprecationWarning` and eventually break. Additionally, naive datetimes stored in the database lose timezone context, making it impossible to correctly display times in the user's local timezone. The same antipattern pre-exists in `models.py` lines 19, 92, 116, 128, but this task adds 2 new instances. Use `datetime.now(datetime.timezone.utc)` for timezone-aware datetimes instead.
- Decision Reason:

### CR-003: update_status accepts arbitrary status strings with no validation
- Status: Resolved
- Description: `meeting_repository.py:27` — `update_status(self, meeting_id: int, status: str)` accepts any string value for `status`. The Meeting model at `models.py:16` has no CHECK constraint on the status column. Calling `repo.update_status(m.id, "bogus")` would silently persist an invalid status to the database. The timestamp logic at lines 31-34 only handles `"active"` and `"finished"`, so invalid values set no timestamps and produce an inconsistent row (status is "bogus" but started_at/ended_at are both NULL). Callers receive no error and no indication that the state is invalid. A whitelist or enum validation at the repository boundary would prevent data corruption.
- Decision Reason:

### CR-004: Fragile test_list_all_returns_desc_order depends on rapid-fire created_at timestamps
- Status: Resolved
- Description: `test_meeting_repository.py:40-46` creates two meetings in rapid succession and asserts `meetings[0].title == "Second"` based on descending `created_at` order. The `created_at` column uses `datetime.utcnow` as default, which has microsecond precision in Python. While unlikely to collide in normal execution, CI environments with mocked/frozen time, virtualized clocks, or extreme test throughput could produce identical timestamps for both creates. When `created_at` values are equal, SQLite's `ORDER BY created_at DESC` ordering is non-deterministic, causing flaky test failures. The test should use deterministic ordering (e.g., explicit sort_order field, or time.sleep between creates, or assert the set of titles rather than positional order).
- Decision Reason: Replaced rapid-fire `repo.create()` calls with direct `Meeting` object construction using explicit `created_at` timestamps 1 month apart (2025-01-01 vs 2025-02-01). The test still verifies descending order via positional assertions (`meetings[0].title == "Second"`, `meetings[1].title == "First"`) as SR-001 requires, but ordering is now deterministic regardless of system clock or CI environment.

### CR-005: has_history VoteRecord check is not meeting-scoped — meeting_id parameter is misleading
- Status: Resolved
- Description: `attendee_repository.py:59-61` — `has_history(self, meeting_id: int, attendee_id: int)` accepts a `meeting_id` parameter, suggesting meeting-scoped history lookup, but the VoteRecord query only filters by `VoteRecord.attendee_id == attendee_id` without joining through `Vote` to scope by meeting. The `VoteRecord` table (models.py:73-79) has no `meeting_id` column; it links to `Vote` via `vote_id`, and `Vote` has `meeting_id`. So an attendee who voted in Meeting A will have `has_history(meeting_B_id, attendee_id) == True` even though they never participated in Meeting B. The ServiceCall check at line 62-64 correctly scopes by both `seat_id` and `meeting_id`, but the VoteRecord check at lines 59-60 does not. Fix: join `Vote` and add `Vote.meeting_id == meeting_id` to the VoteRecord query filter, making the method consistent with its signature contract.
- Decision Reason:

### CR-006: has_history checked_in early return is not meeting-scoped — same class of bug as CR-005
- Status: Resolved
- Description: `attendee_repository.py:57-58` — the `checked_in` early return in `has_history` returns `True` solely based on `a.checked_in` without verifying that the attendee belongs to the given `meeting_id`. If attendee A checked in for Meeting 1 and `has_history(Meeting2_id, A_id)` is called, the method finds attendee A (via `get_by_id`, which is not meeting-scoped), sees `a.checked_in == True`, and returns `True` — incorrectly claiming the attendee has history in Meeting 2. The comprehensive fix: after fetching the attendee, add `if a.meeting_id != meeting_id: return False` so that all subsequent checks (checked_in, VoteRecord, ServiceCall) are implicitly meeting-scoped.

### CR-007: models.py still uses deprecated datetime.utcnow in 5 column defaults

The `datetime` import at models.py line 2 also lacks `timezone`, so the fix requires both import and default callable adjustments (e.g., `default=lambda: datetime.now(timezone.utc)` or a module-level `utcnow` helper). Leaving naive datetimes in column defaults means every row written through column defaults stores timezone-less timestamps, which corrupts time display for users and creates a silent data quality problem that will be expensive to fix later.

### CR-008: has_history ServiceCall check uses seat_id proxy — false positives when attendees share seat_id
- Status: Resolved
- Description: `attendee_repository.py:67-69` — the `has_history` method queries `ServiceCall` by `ServiceCall.seat_id == a.seat_id` to determine whether an attendee made service calls. However, the `Attendee` model (`models.py:46`) has `seat_id = Column(Integer, default=0)` with no unique constraint on `(meeting_id, seat_id)`. The `ServiceCall` model (`models.py:89`) stores `seat_id` but has no `attendee_id` foreign key. This means two attendees within the same meeting can share the same `seat_id` (trivially with the default of 0 for unseated attendees). When attendee A makes a service call at seat X, `has_history` will return `True` for attendee B who shares seat X, falsely attributing A's service call to B. The method signature promises per-attendee accuracy (`attendee_id` parameter) but delivers per-seat accuracy for the ServiceCall path. The `checked_in` and `VoteRecord` paths are correctly scoped post-CR-005/CR-006, but the ServiceCall path inherits this data model limitation. Note: the task spec itself defined this query pattern, so this is a spec-level design issue rather than an implementation deviation, but it remains a correctness bug in production code.
- Decision Reason: Added `attendee_id` column to ServiceCall model (nullable ForeignKey to attendees.id). Updated `has_history` query to filter by `ServiceCall.attendee_id == attendee_id` instead of the seat_id proxy. Updated `ServiceCallCreate` and `ServiceCallOut` schemas to include optional `attendee_id`. Updated `create_service_call` router and `persist_service_call` helper to set attendee_id (persist_service_call looks up attendee by seat+meeting). Updated seed data. Added regression test `test_has_history_service_call_is_attendee_scoped` verifying that two attendees sharing seat_id=0 do not cross-contaminate history.

### CR-009: get_active uses .first() without order_by — non-deterministic when multiple active meetings exist
- Status: Resolved
- Description: `meeting_repository.py:25` — `get_active()` returns `self.db.query(Meeting).filter(Meeting.status == "active").first()` without an `.order_by()` clause. While business logic should enforce at most one active meeting, the database schema (`models.py:16`) has no unique constraint on status, allowing multiple rows with `status = "active"`. Without `ORDER BY`, SQLite may return any matching row, making the result non-deterministic. Adding `.order_by(Meeting.created_at.desc())` (to return the most recently created active meeting) or `.order_by(Meeting.id.desc())` would make the query deterministic regardless of database state. This is a defensive robustness issue — the repository layer should not rely on external guarantees for deterministic query results.
- Decision Reason: Added `.order_by(Meeting.created_at.desc())` to `get_active()` query so it deterministically returns the most recently created active meeting. Added regression test `test_get_active_deterministic_when_multiple_active` with explicit timestamps verifying the newer meeting is returned.

### CR-010: list_by_meeting has no ORDER BY — inconsistent with other list methods, non-deterministic results
- Status: Resolved
- Description: `attendee_repository.py:20-21` — `AttendeeRepository.list_by_meeting()` returns `.all()` without an `.order_by()` clause. This is the only multi-row query in both repositories that lacks explicit ordering: `MeetingRepository.list_all()` orders by `created_at DESC`, `MeetingRepository.get_active()` orders by `created_at DESC` (CR-009), `MeetingRepository.list_agendas()` orders by `sort_order`. Without ORDER BY, SQLite may return attendees in arbitrary order that varies between queries. This can cause UI flakiness (attendee list shifting on refresh) and non-deterministic test behavior. The `test_list_by_meeting` test at `test_attendee_repository.py:32-38` only asserts `len(attendees) == 2`, so positional ordering is untested — if someone later adds positional assertions, the test could flake. Add `.order_by(Attendee.id)` for deterministic id-order, or `.order_by(Attendee.name)` for alphabetical.
- Decision Reason: Added .order_by(Attendee.id) to list_by_meeting() query for deterministic id-order. Added regression test test_list_by_meeting_returns_id_order.

### CR-011: update_status unconditionally overwrites started_at/ended_at on re-activation/re-completion
- Status: Resolved
- Description: `meeting_repository.py:39-42` — `update_status()` unconditionally sets `m.started_at = datetime.now(timezone.utc)` when `status == "active"` and `m.ended_at = datetime.now(timezone.utc)` when `status == "finished"`, regardless of whether those timestamps are already set. This means calling `update_status(m.id, "active")` on an already-active meeting overwrites the original activation timestamp. Similarly, calling `update_status(m.id, "finished")` on an already-finished meeting overwrites the original completion timestamp. Timestamps that record "when did this first happen" are silently corrupted into "when was the last time someone called update_status with this value." The fix: guard each assignment with `is None` (e.g., `if status == "active" and m.started_at is None:`), making timestamps immutable once set so they faithfully record the first state transition.
