### CR-001: MeetingService.end() lacks state validation — can end non-active meetings
- Status: Resolved
- Description: `meeting_service.py:43-61` — the `end()` method calls `self.meeting_repo.update_status(meeting_id, "finished")` without first checking that the meeting is in "active" state. `MeetingRepository.update_status()` does not enforce state transitions (pending → finished is allowed). This means calling `end()` on a meeting that was never started will: reset ALL seats globally (`reset_all_seats`), clear the speaker seat (`clear_speaker_seat`), and close open votes — even though these side effects should only happen when an active meeting ends. If a "pending" meeting is ended, it corrupts seat/speaker state with no corresponding meeting_started event ever having fired.
- Decision Reason: Added state validation — `end()` now fetches the meeting first via `get_by_id()` and checks `meeting.status == "active"` before proceeding. Returns `None` for non-active or non-existent meetings.

### CR-002: Re-seat auto-binding is incomplete — re-checkin always fails
- Status: Resolved
- Description: `seat_service.py:39-49` — `on_seat_vacant()` preserves `attendee_id` on the `SeatState` (for re-seat auto-binding), but does NOT reset `Attendee.checked_in` to `False`. When the same person sits back down and `checkin()` is called again, line 62 (`if att.checked_in: return None`) blocks the checkin because `checked_in` was set to `True` during the first checkin and never cleared on vacate. The auto-bind test (`test_seat_occupied_auto_bind`) only asserts that `seat.attendee_id` is preserved — it never attempts a second `checkin()`, so this gap is untested. End-to-end re-seat flow is broken: the attendee_id is correctly re-associated with the seat, but the user can never complete the checkin.
- Decision Reason: Added `AttendeeRepository.uncheck()` method and call it in `SeatService.on_seat_vacant()` when the seat was in "checked_in" state. This resets the `checked_in` flag to allow re-checkin on re-seat.

### CR-006: No transaction atomicity in MeetingService.end()
- Status: Don't Fix
- Description: `meeting_service.py:43-61` — `end()` performs multiple repository write operations (`update_status`, `reset_all_seats`, `clear_speaker_seat`, `vote_repo.close()` for each open vote), each of which calls `db.commit()` independently. If any operation after the first fails (e.g., `clear_speaker_seat` raises), the meeting status is already committed as "finished" but seats are NOT reset, speaker seat is NOT cleared, and votes are NOT closed. This leaves the system in an inconsistent partial state. The operations should be wrapped in a single transaction or have compensating rollback logic.
- Decision Reason: (1) Attempted reordering side effects before status update — but this creates the inverse problem where seats are reset while meeting remains active if status update fails. (2) Attempted wrapping in a single Session transaction — but each repository method independently calls `db.commit()`, making service-level transaction wrapping impossible without refactoring all repos. (3) Attempted adding per-operation error logging — this detects failures but doesn't prevent partial state. Resolution: full fix requires architectural change where repositories defer commits to the service layer, which is beyond this task scope. The CR-001 fix (state validation before mutation) provides the most critical protection: non-active meetings are rejected. Remaining concerns only apply to rare system-level failures (DB crashes mid-sequence), where idempotent side effects (reset_all_seats, clear_speaker_seat) tolerate retry.

### CR-008: `MeetingService.start()` lacks state validation on target meeting
- Status: Resolved
- Description: `meeting_service.py:31-41` — `start()` only validates that no other meeting is active via `get_active()` but never checks the target meeting's own status. `MeetingRepository.update_status()` does not enforce state transitions (it accepts any status string in `VALID_STATUSES` without checking the current state), so calling `start()` on a "finished" meeting would silently transition it back to "active". This is inconsistent with `end()` (lines 43-64), which was fixed in CR-001 to validate `meeting.status == "active"` before proceeding. The missing guard allows re-animating a finished meeting with its side effects (reset seats, close votes) already executed, producing an inconsistent state where a new "active" meeting has zero votes and reset seats — indistinguishable from a freshly started meeting except for the `ended_at` timestamp.
- Decision Reason: Added state validation — `start()` now fetches the meeting via `get_by_id()` and checks `meeting.status == "pending"` before proceeding. Returns `None` for non-pending or non-existent meetings. Test `test_start_finished_meeting_fails` verifies the fix.

### CR-009: `on_seat_occupied()` lacks state transition guard
- Status: Resolved
- Description: `seat_service.py:19-37` — `on_seat_occupied()` only checks that the seat exists (`if not current`) but does not validate that the seat's current status allows the transition to `occupied_unchecked`. `SeatRepository.update_seat()` has no transition enforcement (it directly sets the status field). This means calling `on_seat_occupied()` on a seat that is already `checked_in` would: (a) downgrade the status from `checked_in` back to `occupied_unchecked`, undoing a completed checkin; (b) publish a duplicate `seat_occupied` event; and (c) start another 3-second `checkin_prompt` timer. In a TOF sensor re-trigger scenario, this corrupts checkin state. The method should guard that `current.status == "vacant"` before proceeding, or at minimum be a no-op when the status is already `occupied_unchecked` or `checked_in`.
- Decision Reason: Added state transition guard — `on_seat_occupied()` now checks `current.status != "vacant"` and returns the current seat state as a no-op if the seat is already `occupied_unchecked` or `checked_in`. This prevents status downgrade, duplicate events, and spurious timers from TOF sensor re-triggers. Tests `test_on_seat_occupied_on_checked_in_seat_noop` and `test_on_seat_occupied_on_occupied_unchecked_noop` verify the fix.

### CR-010: `import threading` inside method body instead of module level
- Status: Resolved
- Description: `seat_service.py:36` — `import threading` is placed inside the `on_seat_occupied()` method body rather than at the module level. While Python caches imports after the first call via `sys.modules`, this is non-idiomatic Python and triggers linter warnings (E402, C0415). Every invocation of `on_seat_occupied()` unnecessarily hits the import machinery — even a cached lookup has a cost. The import should be moved to the top of the file alongside the existing `from sqlalchemy.orm import Session` import.
- Decision Reason: Moved `import threading` to module level (line 3) and removed the inline import from `on_seat_occupied()` method body. All 19 seat service tests pass.

### CR-011: `MeetingService.delete()` has no state validation — can delete active meetings
- Status: Resolved
- Description: `meeting_service.py:69-70` — `delete()` delegates directly to `meeting_repo.delete()` without validating the meeting's state. The `Meeting` model has `cascade="all, delete-orphan"` on all four relationships (agendas, attendees, votes, translation_records). Deleting an active meeting would cascade-delete all associated data without running the `end()` side effects: seats are NOT reset (`reset_all_seats`), speaker seat is NOT cleared (`clear_speaker_seat`), open votes are NOT closed with `vote_closed` events, and no `meeting_ended` event is published. This leaves `SeatState` rows in "checked_in" or "occupied_unchecked" status referencing a now-deleted meeting (seat states are global, not per-meeting), and `SpeakerSeat.seat_id` still set to a value from the deleted meeting. At minimum, `delete()` should reject active meetings (require `end()` first), similar to how `start()` and `end()` validate state. No test covers `delete()` at all — not even a happy path.
- Decision Reason: Added state validation — `delete()` now fetches the meeting via `get_by_id()` and checks `meeting.status != "active"` before proceeding. Returns `False` for active or non-existent meetings. Added 4 tests: `test_delete_active_meeting_fails`, `test_delete_pending_meeting_succeeds`, `test_delete_finished_meeting_succeeds`, `test_delete_nonexistent_meeting_fails`. All 18 meeting service tests pass.

### CR-012: `vote_closed` event payload missing `meeting_id`
- Status: Resolved
- Description: `meeting_service.py:59-62` — inside `MeetingService.end()`, the loop that closes open votes fires individual `vote_closed` events with only `{"vote_id": vote.id}` in the payload. Every other event in both `MeetingService` (`meeting_started`, `meeting_ended`) and `SeatService` (`seat_occupied`, `seat_vacant`, `check_in`, `checkin_prompt`, `speaker_seat_set`, `speaker_seat_clear`) includes `meeting_id` in its payload. The omission breaks the consistent event payload contract and forces `vote_closed` consumers to perform an extra DB lookup to determine which meeting the closed vote belongs to. While `meeting_ended` (which fires shortly after the loop and does include `meeting_id`) provides meeting context, a consumer that subscribes only to `vote_closed` (e.g., a vote-status panel) cannot scope the event to a meeting without additional state management. Adding `"meeting_id": meeting_id` to the payload costs nothing and maintains consistency with all other events.
- Decision Reason: Added `"meeting_id": meeting_id` to `vote_closed` event payload for consistency with all other events. Test `test_vote_closed_event_has_meeting_id` verifies the fix.

### CR-014: `MeetingService.remove_attendee()` can delete attendees from a different meeting
- Status: Resolved
- Description: `meeting_service.py:95-98` — `remove_attendee()` first calls `self.attendee_repo.has_history(meeting_id, attendee_id)` and, if it returns `False`, proceeds to `self.attendee_repo.delete(attendee_id)`. The problem is in what `has_history` returns when the attendee belongs to a *different* meeting: `has_history()` at `attendee_repository.py:63-82` fetches the attendee by ID, checks `a.meeting_id != meeting_id`, and returns `False`. The caller interprets `False` as "no history, safe to delete" and proceeds with the deletion. But when `meeting_id` doesn't match the attendee's actual meeting, the attendee should never be touched — it belongs to another meeting. The result is that `remove_attendee(meeting_id=1, attendee_id=5)` where attendee 5 belongs to meeting 2 will silently delete attendee 5 from meeting 2. The `has_history` method conflates two semantically distinct conditions (no history in this meeting vs. wrong meeting entirely) into a single `False` return. `remove_attendee()` should separately verify that the attendee belongs to the specified meeting before attempting deletion, e.g., by fetching the attendee first and checking `attendee.meeting_id == meeting_id`.
- Decision Reason: Added guard at top of `remove_attendee()` — fetches attendee via `get_by_id()`, verifies `attendee.meeting_id == meeting_id` before proceeding to `has_history` check. Returns `False` for non-existent or wrong-meeting attendees. Tests `test_remove_attendee_wrong_meeting_fails` and `test_remove_attendee_nonexistent_attendee_fails` verify the fix.

### CR-015: `SeatService.on_seat_vacant()` lacks symmetric state guard for already-vacant seats
- Status: Resolved
- Description: `seat_service.py:42-55` — CR-009 added a state transition guard to `on_seat_occupied()` (line 26: `if current.status != "vacant": return current`) to prevent status downgrade and spurious events from TOF sensor re-triggers. However, `on_seat_vacant()` has no corresponding guard. Calling `on_seat_vacant()` on a seat that is already `"vacant"` will: (a) call `update_seat(seat_id, "vacant", ...)` which is a data no-op but still hits the DB with a commit, and (b) publish a spurious `seat_vacant` event. While no data corruption occurs (the seat stays "vacant"), a TOF sensor glitch that fires repeated vacancy events would flood downstream consumers with misleading `seat_vacant` events for seats that were never occupied. The fix is symmetric to CR-009: add `if current.status == "vacant": return current` at the start of `on_seat_vacant()` to make the method idempotent for its terminal state, matching the idempotency that CR-009 provides for `on_seat_occupied()` on already-occupied states.
- Decision Reason: Added state transition guard — `on_seat_vacant()` now checks `if current.status == "vacant": return current` to make the method idempotent for its terminal state, symmetric to CR-009's guard in `on_seat_occupied()`. Test `test_on_seat_vacant_on_already_vacant_noop` verifies the fix — no spurious event, status remains "vacant".
