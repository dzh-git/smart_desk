## Code Review Issues

### CR-001: checkin_prompt WebSocket delivery silently fails due to thread/event-loop mismatch
- Status: Resolved
- Description: The `checkin_prompt` event is published from a `threading.Timer` callback (seat_service.py:37-39) running on a non-asyncio thread. When the EventBridge handler runs in that Timer thread, `_run_async()` at ws_event_bridge.py:57 calls `asyncio.run(coro)` which creates a new event loop. However, `room.send_to_seat()` internally calls `c.ws.send_text()` on WebSocket connections that were accepted on the original FastAPI/uvicorn event loop. WebSocket transports are bound to their accepting loop — sending from a different loop silently fails (the exception is swallowed by EventBus's generic `except Exception` at event_bus.py:105-108). The same issue affects the "broadcast to all rooms" path (ws_event_bridge.py:45-49) when triggered from a non-asyncio thread. The `_run_async` fallback to `asyncio.run()` is architecturally unsound for WebSocket operations — it must use `asyncio.run_coroutine_threadsafe()` with a stored reference to the main event loop, or use `loop.call_soon_threadsafe()`.
- Decision Reason:

### CR-003: No defensive check on event.payload type before calling .get()
- Status: Resolved
- Description: The handler at ws_event_bridge.py:41 calls `event.payload.get("meeting_id")` without verifying that `payload` is a dict. `BaseEvent.payload` defaults to `dict` via `field(default_factory=dict)`, but Python does not enforce type hints at runtime and EventBus.publish() accepts any `BaseEvent` without payload validation. If any upstream code constructs a `BaseEvent` with `payload=None` or a non-dict payload, the handler crashes with `AttributeError`. That exception is swallowed by EventBus's generic `except Exception` handler (event_bus.py:105-108), logged, and silently lost — no WebSocket broadcast occurs and the failure is only visible in logs. A guard like `if not isinstance(event.payload, dict): return` would make the bridge resilient to malformed events.
- Decision Reason:

### CR-004: desk_coordinator._run_async has same thread-safety bug as CR-001 (not fixed)
- Status: Resolved
- Description: The `_run_async` function in desk_coordinator.py (lines 14-23) has the identical thread-safety bug that CR-001 identified and fixed in ws_event_bridge.py. When called from a non-asyncio thread — specifically from `_on_serial` (line 47, invoked by serial thread or FastAPI thread pool via stubs) and from `_schedule_checkin_prompt` (line 76, invoked by `threading.Timer`) — the fallback `asyncio.run(coro)` at line 23 creates a new event loop. WebSocket transports (the connections inside `MeetingRoom`) were accepted on the main uvicorn event loop and are bound to it. Sending WebSocket messages from a different loop silently fails; messages are lost with no error reported. The fix applied to ws_event_bridge.py (capturing the main loop via `asyncio.get_running_loop()` at startup and using `asyncio.run_coroutine_threadsafe()`) should be applied to desk_coordinator.py's `_run_async` as well. This affects all hardware-triggered events (`seat_occupied`, `seat_vacant`, `checkin_prompt`) that flow through the serial → desk_coordinator path, including stub-simulated events from the `/api/debug/simulate/{seat_id}` endpoint (which runs in a FastAPI thread pool).
- Decision Reason: Applied same fix as ws_event_bridge: added `_main_loop` module-level variable, `set_main_loop()` function to capture the event loop at startup, and modified `_run_async` to use `asyncio.run_coroutine_threadsafe()` instead of `asyncio.run()`. Registered `set_main_loop()` call in main.py lifespan. Added 3 new tests in TestDeskCoordinatorRunAsync class verifying ensure_future, run_coroutine_threadsafe, and RuntimeError on missing loop.

### CR-008: main.py ws_endpoint bypasses EventBus for vote_cast and service_call broadcasts
- Status: Resolved
- Description: The `ws_endpoint` handler in `backend/main.py` lines 171-174 and 180-183 calls `room.broadcast()` directly for `vote_cast` and `service_call` WebSocket messages instead of publishing to EventBus. This creates architectural drift: (a) the WebSocket tablet-to-tablet path and REST API path use different broadcast mechanisms for the same logical events, (b) WS type strings (`"vote_update"`, `"service_update"`) are hardcoded in `main.py` rather than managed centrally in `EVENT_TO_WS_TYPE`, and (c) changes to broadcast routing or WS type mapping must be coordinated across two code paths instead of one. Note: the ping/pong on line 156 and the led_sync relay on line 186 are correctly kept as direct WebSocket operations since they are connection-level messages not mapped in EVENT_TO_WS_TYPE. The fix should: (1) have `persist_vote_cast` publish `vote_updated` to EventBus and `persist_service_call` publish `service_call_created` to EventBus, (2) remove the direct `room.broadcast()` calls from `main.py` lines 171-174 and 180-183, and (3) add tests verifying the full pipeline from WebSocket message receipt to EventBus publish to EventBridge broadcast.
- Decision Reason: (1) Added `event_bus.publish(BaseEvent(name="vote_updated", ...))` after db.commit() in persist_vote_cast (votes.py:34-38). Publishes only on successful vote cast. (2) Added `event_bus.publish(BaseEvent(name="service_call_created", ...))` after db.refresh(sc) in persist_service_call (service_calls.py:33-40). (3) Removed direct `await room.broadcast()` calls from main.py ws_endpoint for both vote_cast and service_call — persist functions now publish to EventBus, EventBridge handles broadcast. (4) Created new test file test_persist_eventbus_publish.py with 3 tests: publish on success, no publish on invalid vote, and service_call publish verification. All 239 non-integration tests pass (7 integration test failures are pre-existing API format mismatch). App starts cleanly (Step 4: OK).
