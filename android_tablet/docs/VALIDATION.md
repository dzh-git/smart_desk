## 实施过程中的困难与解决方案

### 1. Gradle 找不到 Java

**现象**：直接执行 `gradlew.bat` 时提示 `JAVA_HOME is not set`，系统 PATH 中也没有 `java`。

**原因**：Android Studio 安装在非默认目录，JDK 使用 Android Studio 自带的 JBR，而不是系统独立 JDK。

**解决方案**：确认 JBR 路径为：

```text
D:\Program Files\Android\Android Studio\jbr
```

构建前设置 `JAVA_HOME`，不另外安装 JDK。

### 2. Gradle 缓存目录受到沙箱权限限制

**现象**：Gradle 无法创建用户目录下的 wrapper lock 文件：
`Could not create parent directory for lock file ...\.gradle\wrapper\dists`。

**解决方案**：在用户授权后使用提升权限执行 Gradle，让构建复用用户目录中的 Gradle 缓存；项目生成物仍写入工作区。

### 3. 并发构建导致 APK 产物版本不一致

**现象**：源代码已经是 0.3.1，但设备中仍显示 0.3.0；随后覆盖安装又出现调试签名不一致。

**原因**：前一次构建超时后 Gradle 子进程仍在运行，多个构建进程同时写入同一个 `app-debug.apk`，并且不同构建进程生成了不同的 Debug 签名状态。

**解决方案**：停止重复构建，使用 `--no-configuration-cache` 和单个后台构建进程强制重新打包；用 `aapt dump badging` 和 `dumpsys package` 双重核对版本号。签名不一致时卸载旧的测试包再安装新版。该卸载只清除了原型应用的测试状态。

### 4. MIUI 拦截 ADB 安装

**现象**：Redmi K60 返回 `INSTALL_FAILED_USER_RESTRICTED: Install canceled by user`，即使“USB 安装”开关已打开。

**解决方案**：确认设备保持解锁并重新触发安装；仍被 MIUI 拦截时，将 APK 推送到手机 `Download` 目录，由用户在文件管理器中手动确认安装。代码构建本身不受影响。

### 5. 摄像头预览层遮挡 React 状态页面

**现象**：启动摄像头后页面只显示固定文字“正在本地检测人脸 · 请正对摄像头”，看不到 React 中实时更新的检测状态。

**原因**：原生 `cameraOverlay` 是全屏层，覆盖了 WebView；其顶部 `TextView` 使用固定字符串。

**解决方案**：给原生提示增加 ID，并在 Android 收到检测结果后动态显示“未检测到人脸 / 已检测到 1 张人脸 / 已检测到多张人脸”和耗时，同时继续向 React 回传 JSON。

### 6. 人脸状态在单帧结果之间快速抖动

**现象**：空场景日志中 `NO_FACE` 与 `ONE_FACE` 快速交替，偶尔还出现异常的多脸数量；单帧结果直接更新 UI 会放大误报。

**解决方案**：先记录原始检测结果，再加入三项简单过滤：

- `minFaceSize=0.3`；
- 必须同时检测到左眼、右眼和鼻子关键点；
- 同一状态连续 3 次才回传。

0.3.2 版本空场景约 45 秒测试中，过滤后的阳性误报为 0 次。该参数会要求人脸更靠近镜头并尽量正对摄像头。

### 7. ImageAnalysis 异步资源释放容易遗漏

**风险**：ML Kit 是异步处理，若在成功、失败、停止或异常路径中漏掉 `ImageProxy.close()`，可能造成帧堆积、内存增长或停止后仍处理旧帧。

**解决方案**：统一在 ML Kit task 的 complete 回调和提交异常路径关闭 `ImageProxy`；停止时先清空 analyzer，再解绑 CameraX，最后关闭 detector，并用 5 次启停和停止后日志验证资源释放。

### 8. 当前方案的边界

ML Kit Face Detection 只负责检测图像中的脸。0.5.0 已接入并强化 MobileFaceNet
做 1:1 身份验证，但仍不具备活体检测能力；照片或屏幕翻拍可能通过。仍需用户在
真实正脸、非注册人员、两人同时入镜和至少 30 分钟连续运行条件下完成最终验收。

### 9. MobileFaceNet 模型规格与来源不统一

**困难**：网络上的同名 MobileFaceNet 模型可能使用 128、192 或 512 维输出，
输入归一化也不完全一致。如果仅按文件名接入，轻则比对分数异常，重则直接发生
张量尺寸错误。

**解决方案**：早期版本先核对参考推理代码和真机张量；0.8.0 已进一步固定为
`[1,112,112,3] → [1,256]` 的 SE-MobileFaceNet embedding 模型，使用
`(value-127.5)/128` 归一化。模板绑定模型 SHA-256 和pipeline版本，原192维
模板自动失效。

### 10. 旋转坐标与人脸对齐必须在同一坐标系

**困难**：ML Kit 使用 `rotationDegrees` 检测，而 CameraX 原始 Bitmap 仍是传感器
方向。直接用检测框裁剪原图会截取错误区域，尤其在 Redmi K60 当前 270° 分析
方向下更明显。

**解决方案**：先按 `ImageProxy.imageInfo.rotationDegrees` 将 Bitmap 旋转到正向，
再使用 ML Kit 的边界框；根据左右眼连线计算角度，将人脸旋转至水平并缩放到
112×112。裁剪结果只在内存中用于一次推理，随后立即回收。

### 11. 注册和验证不能用单帧决定

**困难**：单帧会受眨眼、运动模糊、姿态和自动曝光影响，直接保存一帧或凭一帧
判断会造成分数抖动。

**解决方案**：早期版本逐步验证了多帧注册和连续帧判定；0.8.0 最终固定为每个
光照阶段采集5帧、删除一致性最低的一帧并聚合其余4帧，验证时还要求5帧中至少
4帧的Top1人员一致。

### 14. 固定 0.65 阈值造成较高误识别

**现象**：第一版只验证了本人通过，没有使用非注册人员分数标定；0.65 对当前
模型和拍摄环境过于宽松。

**解决方案**：早期版本曾临时提高阈值并增加五点对齐和质量门槛，但模型更换后
不再沿用任何旧阈值。0.8.0 在 `CALIBRATION_PENDING` 状态禁止返回
`VERIFIED`，必须使用新模型重新完成75次原型标定后才能应用 `PROVISIONAL`
阈值。

### 12. 模型许可与生物特征安全边界

**困难**：原始 MobileFaceNet 代码为 Apache-2.0，但当前转换模型的来源仓库没有
单独说明模型权重的训练数据和再分发许可。

**解决方案**：在 APK 资产中记录来源、规格和 SHA-256，并把该权重限定为技术
原型验证。当前模板保存在 App 私有目录且不保存照片；正式商用前必须换成许可和
训练数据来源明确的模型，并用 Android Keystore 加密生物特征模板。

### 13. Windows 中文用户目录导致 Gradle 测试进程失败

**现象**：Android 主代码、测试代码和 APK 都能编译，但 Gradle 9.4.1 启动
`Gradle Test Executor` 时出现乱码并找不到
`worker.org.gradle.process.internal.worker.GradleWorkerMain`。

**解决方案**：将 `GRADLE_USER_HOME` 和 `ANDROID_USER_HOME` 实际迁移到工作区
内的纯ASCII目录，并使用进程内Kotlin编译策略。最终15个JVM单元测试全部通过，
Android Lint和APK构建也通过。

### 15. 光线变化导致本人分数落在固定阈值附近

**现象**：同一人在冷灰背景和暖色侧光下，相似度中位数约为 0.77–0.79，
低于原固定阈值 0.80；部分后续帧又能恢复到 0.83 以上。单次 5 帧窗口会过早
给出失败结果。

**解决方案（0.7.0）**：

- CameraX 将 AF/AE/AWB 测光区域固定在圆形引导区中心，降低圈外明暗背景对
  人脸曝光和白平衡的影响；设备不支持 AWB 区域时自动回退为 AF/AE。
- 圆圈判定使用“严格进入、宽松保持”，保持范围放宽 18%，并在人脸短暂越界或
  漏检时保留 750 ms，避免检测框抖动立即清空身份窗口。
- 强通过阈值调整为 0.82，最近 5 帧至少 4 帧达到阈值才通过；0.65–0.82
  作为灰色区间继续收集，最多采集 15 帧；中位分不高于 0.65 时可提前拒绝。
- 已通过状态使用 0.75 保持阈值和 5 帧中位数，单帧光照波动不会立即撤销结果。

**边界**：上述措施只减少曝光波动、框选抖动和过早拒绝，不能代替多光照模板、
活体检测或正式的多人 FMR/FNMR 标定。

### 16. 第一阶段双光照多人验证升级（0.8.0）

**模型困难**：ArcFace是训练损失/分类头名称，直接按文件名转换可能误把训练身份
logits当作人脸特征；原模型还使用mixed-float16层策略。

**解决方案**：固定 Keras_insightface v1.0.0 的
`se_mobile_facenet` 256维 `basic_model` 文件、大小和SHA-256。转换脚本确认
最终层为 `embedding`，强制float32策略，并断言
`[1,112,112,3] → [1,256]`。10张不同合成人脸上的Keras/TFLite最低余弦一致性
为1.0；这些图片只用于数值等价检查，不用于准确率标定。App启动时再次校验TFLite
哈希、张量形状和有限非零输出。

**光照困难**：同时把当前人脸与自然光、补光模板比较并取最大值，会把9人搜索
扩大为18次机会并抬高陌生人的偶然最高分。

**解决方案**：自然光阶段只与9人的 `normal` 模板比较；自然光未通过后，补光
阶段只与9人的 `fillLight` 模板比较。Top1和Top2按人员计算，同一人的两个模板
不会互相占据排名。

**采集困难**：测光命令发出后立即取帧会记录仍在变化的曝光；5张相邻帧也可能
近乎相同。

**解决方案**：中央测光后固定等待400ms，再要求最近3张对齐脸亮度极差小于15；
每约180ms取一张，共5张，删除一致性最低的一张并聚合其余4张。稳定等待超过
1秒、采集中离圈、圆内多人或关键点中断时返回 `RETRY_REQUIRED`，不降低要求。
补光时圆圈外显示白色并将屏幕临时调至100%，所有退出路径恢复原亮度。

**真机时序困难**：CameraX完成绑定时，`PreviewView` 可能尚未完成首次布局，
此时无法生成中央测光点。

**解决方案**：首次测光增加最多5次、每次100ms的有限布局重试；每次正式采集
开始时仍会重新请求中央测光。若设备处于AOD/Dozing且界面始终没有布局，则跳过
本次后台测光，待用户点亮屏幕并开始采集后再执行，不进行无限重试。

**标定边界**：3名注册人员、2名陌生人、3种环境、每人5次共75次，只能产生
`PROVISIONAL` 原型阈值。标定前不返回 `VERIFIED`；应用原型阈值后也必须携带
`verificationLevel=PROTOTYPE`。`VALIDATED` 预留给未来扩大独立测试后的受控
流程，当前页面不能设置。

**隐私与许可**：Debug诊断默认关闭，仅在App私有目录保存对齐PNG和JSONL，
可一键清除；正式流程仍不保存照片。代码许可与权重许可分别记录，当前MS1MV3
权重仅允许非商业研究原型，不能直接进入商业部署。
