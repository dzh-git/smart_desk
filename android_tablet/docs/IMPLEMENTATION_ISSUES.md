# 实施问题与解决方案总结

本文汇总 SmartDesk Tablet Prototype 从摄像头检测原型升级到 0.8.0
双光照、多人开放集验证及单人静态代理诊断过程中遇到的主要问题。详细测试日志
仍保留在 `VALIDATION.md`，静态图片数据见 `STATIC_IMAGE_TEST_REPORT.md`。

## 一、构建、安装与设备环境

### 1. Android Studio 位于非默认目录，Gradle 找不到 Java

**问题**：系统没有配置独立 JDK，直接运行 Gradle 提示 `JAVA_HOME is not set`。

**解决方案**：固定使用 Android Studio 自带 JBR：

```text
D:\Program Files\Android\Android Studio\jbr
```

Android SDK 固定为 `D:\Android\Sdk`，避免再安装一套版本不同的 JDK。

### 2. Windows 中文用户目录导致 Gradle 测试进程启动失败

**问题**：Gradle Test Executor 在包含中文字符的默认用户缓存路径中出现乱码，
无法找到 `GradleWorkerMain`。

**解决方案**：将 Gradle 和 Android 的工作目录迁移到工作区内的纯 ASCII 路径：

```text
D:\Ai_project\android_test\.gradle-user-home
D:\Ai_project\android_test\.android-user-home
```

并使用进程内 Kotlin 编译策略。最终 15 个 JVM 单元测试、Lint 和 APK 构建均已
通过。

### 3. Vite 在受限环境中无法创建子进程

**问题**：前端执行 `vite build` 时出现 `spawn EPERM`，不是代码编译错误。

**解决方案**：仅对已经确认的 `npm run build:android` 构建命令授予执行权限。
前端构建成功后，再把静态文件复制到 Android assets。

### 4. 并发构建和不同调试证书造成覆盖安装失败

**问题**：超时后的旧 Gradle 进程仍可能继续写 APK；不同调试密钥生成的 APK
无法覆盖设备上已安装的版本。

**解决方案**：保持单个构建进程，构建后核对 versionCode/versionName；最终 APK
统一使用设备上原应用对应的调试证书签名，并在安装后通过 `dumpsys package`
再次确认版本。

### 5. MIUI/HyperOS 对 USB 安装和输入事件有限制

**问题**：即使已经打开 USB 安装，系统仍可能返回
`INSTALL_FAILED_USER_RESTRICTED`；设备处于 AOD 时，ADB 也不能代替用户解锁。

**解决方案**：安装时保持设备点亮、解锁并确认系统弹窗。自动测试只负责构建、
签名、安装和启动；涉及解锁、真人采集及安装确认的操作由用户完成。

## 二、摄像头、人脸检测与对齐

### 6. 原生摄像头层遮挡 Web 状态页面

**问题**：全屏 CameraX overlay 覆盖 WebView，用户只能看到固定提示，无法看到
实时检测和身份状态。

**解决方案**：原生层继续显示实时人脸提示，同时通过 Android Bridge 向 React
发送结构化事件；React 页面展示采集阶段、进度、Top1/Top2、分差和标定状态。

### 7. 空场景偶发被判断为存在一张人脸

**问题**：单帧 ML Kit 检测结果会抖动，远处纹理或不完整候选框可能造成短暂
误报。

**解决方案**：采用三项简单过滤：

- `minFaceSize=0.3`；
- 至少存在双眼和鼻子关键点；
- 相同状态连续出现3次才更新稳定状态。

该措施降低了空场景误报，但也要求使用者更靠近镜头并保持正脸。

### 8. 复杂背景中的其他人员会干扰验证

**问题**：实际会议环境中，目标人员身后可能还有其他人；直接要求整幅画面单脸
会造成大量无意义失败。

**解决方案**：只处理中央圆圈中的人脸，圈外人员完全忽略；圆内恰好一人时继续，
圆内多人时暂停并返回 `RETRY_REQUIRED`。圆圈采用严格进入、宽松保持和短暂离圈
缓冲，减少检测框抖动。

### 9. ML Kit 检测坐标与原始摄像头图像方向不一致

**问题**：Redmi K60 分析帧可能带有 270° 旋转；直接用检测框裁剪原始 Bitmap
会得到错误的人脸区域。

**解决方案**：先根据 `rotationDegrees` 把图像旋转到检测坐标系，再进行镜像处理、
五点标准对齐和 112×112 RGB 裁剪。注册和验证调用完全相同的预处理实现。

### 10. CameraX 刚绑定时中央测光点尚不可用

**问题**：CameraX 已绑定不代表 `PreviewView` 已完成布局；宽高为0时无法创建
中央 AF/AE/AWB 测光点。设备处于 AOD/Dozing 时尤其明显。

**解决方案**：首次测光最多重试5次、每次间隔100ms；正式采集开始时再次请求
中央测光。若屏幕一直处于 AOD，则停止后台重试，等待用户点亮屏幕后再采集。

### 11. ML Kit 异步任务容易遗漏帧资源释放

**问题**：任何成功、失败或停止路径漏掉 `ImageProxy.close()`，都可能造成帧堆积、
停止后继续处理或内存增长。

**解决方案**：在任务 complete 回调和提交异常路径统一关闭帧；停止时依次清空
analyzer、解绑 CameraX、关闭 detector，并通过重复启停检查日志。

## 三、模型选择、转换与预处理

### 12. “MobileFaceNet + ArcFace”不能唯一确定部署输出

**问题**：ArcFace主要是训练损失或分类头名称。同名模型可能输出128、192、256、
512维 embedding，也可能输出训练数据集身份 logits。

**解决方案**：固定 Keras_insightface v1.0.0 的确切 256维
`se_mobile_facenet` `basic_model` 文件，记录完整来源URL、文件名、大小和
SHA-256。转换前强制断言最终层为 `embedding`，拒绝分类模型。

### 13. 源模型使用 mixed-float16，不能直接假定输出为 FP32

**问题**：直接转换可能保留混合精度策略，造成 Android 输入输出类型或数值行为
不一致。

**解决方案**：转换脚本把模型配置克隆为 float32，禁止量化，明确要求 TFLite
输入输出均为 float32，并断言：

```text
[1,112,112,3] RGB → [1,256] embedding
```

### 14. 仅成功转换不能证明两个模型输出等价

**问题**：TFLite 文件能够加载，不代表层选择、预处理或转换结果正确。

**解决方案**：使用10张不同的112×112合成人脸同时运行 Keras 和 TFLite，
逐张检查维度、NaN/Inf、零向量和余弦一致性。最低余弦一致性为1.0。合成图仅用于
转换数值等价验证，不用于识别准确率或阈值标定。

### 15. 模型文件可能被误替换或配置与二进制不一致

**问题**：只按 assets 文件名加载模型，无法发现文件被替换或错误打包。

**解决方案**：App 启动时验证模型 SHA-256、输入形状、输出形状、数据类型及一次
有限非零输出。APK 中只保留新的256维模型；旧192维模型资源已移除。

## 四、采集、模板与身份判断

### 16. 单帧识别对曝光、眨眼、模糊和关键点误差过于敏感

**问题**：单帧可能让本人分数突然下降，也可能让陌生人偶然获得较高分。

**解决方案**：每个阶段间隔约180ms采集5个合格 embedding，计算每帧与其余帧的
平均余弦一致性，删除最低的一帧，平均其余4帧并再次 L2 归一化。

### 17. 测光后立即采集会把曝光变化写入模板

**问题**：AE/AWB 调整需要时间，连续帧也可能几乎完全相同。

**解决方案**：中央测光后等待400ms，并要求最近3帧人脸平均亮度极差小于15；
稳定等待超过1秒则返回 `RETRY_REQUIRED`，不降低质量条件继续采集。

### 18. 光线变化使单一模板的本人分数明显下降

**问题**：自然光模板在偏亮冷光或偏暗暖光下可能失配。

**解决方案**：注册自动生成 `normal` 和 `fillLight` 两个模板。补光阶段把屏幕
临时调到100%并显示白色补光层，重新测光后采集；成功、失败、停止及生命周期退出
路径都恢复原屏幕亮度。

### 19. 两个模板无条件取最大值会增加陌生人误接受机会

**问题**：9人各有两个模板时，无条件取最大值相当于从18个候选中寻找最高分，
本人和陌生人的偶然最高分都会被抬高。

**解决方案**：严格同条件匹配：

```text
自然光阶段 → 只比较 normal
补光阶段   → 只比较 fillLight
```

Top1和Top2始终按人员排名，同一个人的两个模板不会分别占据Top1和Top2。

### 20. 只选择最高分会把陌生人强行识别为某个注册人员

**问题**：闭集“最高分即身份”的方式不适合实际会议环境。

**解决方案**：每个阶段同时要求：

```text
Top1达到当前阈值
AND Top1 - Top2 >= 0.05
AND 5帧中至少4帧的Top1人员一致
```

Top1低于阈值返回 `UNKNOWN`；分差不足、身份不一致或采集不稳定返回
`RETRY_REQUIRED`。少于2名已注册人员时不开放正式Top1/Top2验证。

### 21. 模型升级后旧模板维度和分数空间不再兼容

**问题**：继续读取旧192维模板会造成维度错误，或者误以为旧阈值仍然有效。

**解决方案**：模板绑定模型 SHA-256 和 pipelineVersion 3；旧模板自动忽略。
重新注册时两个新模板原子覆盖，任何一阶段失败都不写半成品。最多保存9人。

### 22. 小样本阈值容易被误当成正式安全结论

**问题**：3名注册人员和2名陌生人的75次测试不足以估计开放集误接受率。

**解决方案**：明确三种状态：

```text
CALIBRATION_PENDING → PROVISIONAL → VALIDATED
```

标定前禁止返回 `VERIFIED`；75次测试只能设置 `PROVISIONAL`，并携带
`verificationLevel=PROTOTYPE`。本版本没有普通接口可以设置 `VALIDATED`。

## 五、隐私、许可与当前边界

### 23. 调试图像有助于定位问题，但会增加隐私风险

**解决方案**：诊断模式默认关闭。只有手动开启后才在 App 私有目录保存112×112
PNG和JSONL指标，并提供一键清除；正式流程不保存人脸照片。

### 24. 代码许可证不等于预训练权重可以商用

**解决方案**：模型卡分别记录代码MIT许可证和MS1MV3权重的非商业研究限制。
当前实现仅用于内部原型，商业部署必须更换许可、训练数据和再分发条件明确的权重。

### 25. 当前方案仍不具备正式安全系统能力

当前没有活体检测，照片或屏幕翻拍仍可能攻击系统；模板尚未使用 Android
Keystore加密；75次测试也不能证明正式FMR/FNMR。正式部署前仍需扩大陌生人和
独立样本测试、增加活体检测、模板加密及商业模型许可审查。

### 26. 现场暂时只有一名注册人员

**问题**：无法凑齐3名注册人员和2名陌生人，不能执行75次多人开放集标定。

**解决方案**：增加只读离线图片诊断工具，读取当前注册模板，使用同一个256维
TFLite模型、相同五点标准坐标和预处理，比较10张本人图片与10张许可明确的
Pexels肖像。本人10张全部检测并通过质量门槛；合格网络陌生人最高分仍明显低于
本人最低分。该测试只检查明显误匹配和质量门槛，结果固定标记为代理诊断，禁止
生成 `PROVISIONAL` 阈值。详细结果见 `STATIC_IMAGE_TEST_REPORT.md`。

### 27. 相册样本顺序与身份标签不能靠文件名推断

**问题**：相册同时存在相机照片、App截图和此前测试图片。如果只按文件名或目录
选取，可能把旧截图、网络图片或质量控制图片错误标记为本人样本，导致分数统计
失真。

**解决方案**：通过 Android MediaStore 按媒体时间倒序查询当前相册前10项，
只读提取到被Git忽略的本地测试目录，逐张查看并由用户确认身份后再标记为
`USER_GENUINE_PROXY`。本轮确认前5张为当前相机自拍，后5张为App注册/验证截图，
随后重新生成完整JSON结果和测试报告。测试图片不写回设备、不打包进APK。

### 28. 戴眼镜注册后，摘下眼镜的本人分数明显下降

**问题**：当前注册模板主要来自戴眼镜状态。最新5张相机自拍中，4张戴眼镜照片
的 `normal` 分数为0.7510–0.8181，而未戴眼镜照片为0.6741；
`fillLight` 分数也从戴眼镜照片的0.7544–0.8156下降到0.6317。这说明配饰变化
会影响当前特征空间，不能只按理想光照样本估计本人下界。

**解决方案**：没有通过降低阈值掩盖问题，也没有把眼镜状态新增为第三个模板并
扩大匹配机会。当前原型建议按日常主要佩戴状态注册，同时把戴眼镜和未戴眼镜样本
都纳入后续独立测试；在多人数据足够前继续保持 `CALIBRATION_PENDING`。若后续
两种状态仍稳定分离，再评估重新注册或受控的外观模板方案，并重新统计陌生人最高
分。

### 29. 离线图片诊断无法完全复现 App 的实时检测链路

**问题**：静态工具使用OpenCV YuNet检测五点，而App使用ML Kit并通过CameraX
连续采集。两种检测器的关键点位置、实时曝光、帧间稳定性和4/5身份一致性条件
均不完全相同。

**解决方案**：离线工具只复用相同的112×112标准坐标、RGB归一化、256维TFLite
模型和L2归一化，不把离线相似度直接写入App阈值。报告明确标记
`STATIC_IMAGE_PROXY_DIAGNOSTIC` 和 `calibrationAllowed=false`；App状态继续保持
`CALIBRATION_PENDING`，最终仍需真人CameraX 5+5采集与多人现场测试。

## 六、最终验证结果

- 前端生产构建通过。
- Android单元测试：15项通过，0失败。
- Android Lint和Debug APK构建通过。
- Redmi K60覆盖安装和0.8.0启动通过。
- 真机模型加载形状为 `[1,112,112,3] → [1,256]`，预热约24ms。
- Android Bridge人员列表、状态、诊断开关接口通过。
- CameraX前置摄像头启动与停止通过，未发现崩溃。
- 相册前10张本人图片均完成离线检测并通过质量门槛；与本轮10张网络代理肖像
  存在明显探索性分数间隔，但没有据此应用阈值。
- 真人5+5注册、三种光照和75次原型标定仍需现场参与者完成，不能用模拟数据代替。
